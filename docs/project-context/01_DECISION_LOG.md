# Ясномера — журнал решений

Обновлено 31.10.2026. «В main» подтверждается Git; «прототип/направление» не означает production. Внешняя продуктовая история указана отдельно от репозитория.

| Решение | Почему | Основание и состояние |
| --- | --- | --- |
| Независимые образовательные расчёты; «Понятные расчёты для финансовых решений» | Пользователь должен понять экономику решения без давления продаж | `docs/PROJECT_FOUNDATION.md`, README, миграция бренда PR #76; в main |
| Не банк, брокер, советник, лидогенератор | Не создавать ложного впечатления предложения продукта/персональной рекомендации | PR #47, #48, Foundation; удалены фиктивные заявки, сбор контактов, партнёрская имитация и синтетические банковские ставки |
| Официальные первичные данные с provenance и явными статусами | Правдоподобное число не заменяет проверенный факт | PR #50, #51, #54; schema v2, `ok/stale/unavailable`, проверки источников и дат; в main |
| Fail-closed и атомарная публикация | Невалидный кандидат не должен вытеснять последний проверенный набор; после hard TTL финансового payload нет | `data_validation/validate.js`, policies, updater-ы, PR #54; в main, не ослаблено текущим PR |
| Детерминированные тесты владеют полным fixture | Ежедневный корректный переход production JSON в stale/unavailable не должен менять смысл unit-теста и блокировать все обновления | PR #91, merged 30.10; изолированы payload, статус, даты и охват в обоих data-validation test-файлах |
| Ставка ЦБ — справочный факт, не ставка ипотеки | Не подменять параметры пользователя и реальные предложения банков модельным спредом | PR #48 и текущий mortgage; в main; B+ сохраняет смысл, размещает справку ближе к вводу |
| Снять некорректный ипотечный налоговый вычет | Не завышать экономию неподтверждённой методологией | PR #55; в main. Возврат потребует отдельной методологии и решения |
| Проценты и страховка показываются отдельно | Обязательный платёж не включает страховку; расходы на кредит должны быть объяснимы | PR #79 (`8a6c1b2`); в main. Общие выплаты по новой ипотеке не включают первоначальный взнос |
| Сохранять новую/действующую ипотеку, комфортный платёж, месяцы, страховку, графики и таблицу | Упрощать восприятие через иерархию, сохраняя полезную функциональность | Текущий `mortgage.html`, B+/Final brief; production-функции, сохранение обязательно для будущего редизайна |
| Обязательный месячный платёж — главный результат будущего дизайна | Холодному посетителю сначала нужен ответ на вопрос о ежемесячной нагрузке; красная переплата не должна доминировать | Принято в дизайн-чатах B/B+/Final. Реализовано в ветке codex/mortgage-hybrid-redesign от 31.10; main/production до её merge сохраняют прежний интерфейс |
| Базовый расчёт отделён от досрочного сценария | Пользователь должен понимать базовые условия и эффект своего действия, а не смешивать их | B/Final direction; договорный срок в hero, сокращённый срок только в эффекте досрочных. Реализовано в implementation-ветке 31.10, ещё не в production |
| Регулярные и разовые досрочные — отдельные задачи | Их не обязательно заполнять вместе; разовая доплата должна быть обнаружима через график | B+ Final: регулярные выше по приоритету; отдельный контейнер разовых, месяц+сумма, список, «Выбрать месяц в графике». | Обе стратегии досрочного погашения остаются | Сокращение срока и уменьшение платежа отвечают разным целям | Production + B+/Final; не удалять ни одну и не менять алгоритм ради визуального упрощения |
| PNG/share — обязательные, видимые вторичные действия | Результат должен сохраняться и воспроизводиться вне экрана калькулятора | PR #77, #79, #87; общий clone-based export в main. Дизайн-экспорт не заменяет production-контракт |
| PNG рендерится с изолированного клона | Не ломать живую страницу, скролл и графики; сохранять полный состав результата | `js/ui-utils.js`, ui-state tests; в main. Захват `results-panel`, не только внутреннего `screenshot-area` |
| Расчёт и отрисовка имеют разные ошибки | Недоступность Chart.js не должна превращать корректную финансовую модель в ошибку расчёта или ложную конверсию | PR #89, mortgage diagnostics/tests; в main |
| `calculate_success` после валидного пользовательского результата, один раз | Автоматический пример/невалидный ввод не должны завышать конверсию | PR #79, #89; в main для ипотеки. Categorical diagnostics — params, не goals |

| B+ UX + узнаваемая визуальная ДНК Ясномеры | Слишком воздушная светлая тема и слабая граница разовых доплат создавали ощущение отдельного сайта | «PM 2.0»: 31.10 утверждены hybrid desktop/mobile images + B+ UX; реализовано в ипотечном PR |

## Как дополнять журнал

Для нового решения записывать причину, источник (PR/commit или датированное сообщение владельца), статус «production / main / PR / prototype / proposal» и способ проверки. Не выдавать будущий roadmap за выполненную работу. Состояние аккаунтов, метрики и цены без новой проверки не переносить из старого чата как текущий факт.
